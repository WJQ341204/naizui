# 优化意见与实施方案（OPTIMIZATION）

> 版本基线：v12.3 + 已修 P17（ffprobe 解码）+ 种子确定性修复 ｜ 整理日期：2026-09-26
> 所有「现状」均来自**实际代码核查**与**真实运行数据**，非泛泛而谈。

## 零、现状核查结论（方案依据）

| 核查项 | 实测结果 | 影响 |
|---|---|---|
| `_wan5b` 失败重试 | **无**（对比 `_wan_a14b` 有 `max_retries=2` + 退避 5s/10s） | 一次失败即降级 |
| 降级是否记录原因 | **否**（`scene.error_msg` 保持为空） | 静默降级，用户不知情 |
| 真实降级率 | 12 场景中 **1 个**（场景 05）走 ken_burns = **8.3%** | 成片质量不确定 |
| TTS 缓存 | **无** | 重复跑重复消耗额度 |
| TTS 并发 | 串行（12 段实测 39s） | 可压缩到 ~10s |
| 关键帧生成 | 串行（`main.py:7658` 为保持角色锚点连贯） | 无法并发提速 |
| 单场景耗时 | 12-17 min（采样≈8min + VAE 解码 3min + RIFE/超分 24s） | 12 场景 ≈ 3h |
| 中间文件清理 | 曾因全局通配 `*_faded*` 误删他场景 → QA 全 fail → **12 场景全重跑** | 最贵的一类事故 |

## 一、P0：静默降级治理（质量风险最高，建议优先）

### 问题
`scripts/video_engine.py` 的 wan5b 分支：

```python
r = await _wan5b(scene, scene_dir, job, ctx)
if r:
    scene.video_mode_used = "wan5b"
    return r
# 失败 → 直接降级，且【不记录任何原因】
r = await _ken_burns(...)
scene.video_mode_used = "ken_burns"
```

后果：**成片里混着"静态图+推拉"的假视频，而出片报告看不出来**。实测 8.3% 命中率。

### 方案
1. **补重试**：给 `_wan5b` 加与 `_wan_a14b` 一致的 `max_retries=2` + 指数退避，每次重试换 seed（避免同一噪声卡死）
2. **记录降级原因**：降级时写 `scene.error_msg = f"wan5b 失败（{原因}），已降级 ken_burns"`
3. **升级计数**：job 增加 `degrade_count` 字段，出片前汇总「真视频 N/M」
4. **严格模式**：新增 `STRICT_VIDEO_MODE` 开关，开启后宁可整条失败也不降级（用于交付级出片）

### 收益 / 成本
- 收益：8.3% 降级率有望降到 <2%；消除"出完片才发现有静态图"
- 成本：**低**（约 40 行改动）

## 二、P1：渲染提速（体验瓶颈最大）

### 问题
12 场景约 **3 小时**。拆解后大头在采样与 VAE 解码，而非后处理。

### 方案（按性价比排序）
| # | 措施 | 预估收益 | 风险 |
|---|---|---|---|
| a | **步数分级**：情绪峰值/反转场景 30 步，过渡/环境场景 20 步 | 省 25-30% | 低（过渡镜头本来就看不清细节） |
| b | **超分改为可选**：1408×2560 已是竖屏高清，2x 超分收益递减 | 省 RIFE+超分段约 24s/场景 | 低，提供开关即可 |
| c | **分辨率分级**：远景/环境镜头降一档 | 采样时间近似平方级下降 | 中，需目视验收 |
| d | **关键帧并发**：把"上一张做锚点"改为**固定参考图做锚点**，从而允许 2-3 并发 | 图片阶段省 50%+ | 中，可能影响连贯性，需 A/B 对比 |

### 收益 / 成本
- 收益：3h → **1~1.5h**
- 成本：中（需目视验收画质，建议先做 a+b，风险最低）

## 三、P2：TTS 并发 + 缓存（最便宜的提速）

### 问题
12 段串行 39 秒；无缓存导致同一段台词反复烧额度；长文本 >900 字切段后 ffmpeg 拼接可能有接缝。

### 方案
1. **并发**：`asyncio.gather` + 信号量限 3-5（TTS 是网络 IO，瓶颈在 RTT 不在本地）
   → 39s 压到 **~10s**
2. **缓存**：key = `md5(text|voice|mood|intensity|rate)`，命中直接复用，落 `output/_tts_cache/`
   → 重复跑零消耗
3. **消除接缝**：切点固定在句末标点；段间插入 80-120ms 静音；拼接后做一次响度归一化

### 收益 / 成本
- 收益：快 3-4 倍 + 省额度 + 消除接缝
- 成本：**低**（约 60 行，且不影响现有回退链）

## 四、P3：中间文件与清理治理（稳定性）

### 问题
曾发生：Step 7 清理用全局通配 `*_faded*`，误删其他场景中间文件 → QA 全 fail → **12 场景全部重跑（3 小时白跑）**。
虽已收窄为 `scene_{id:03d}_` 前缀，但清理逻辑仍散落在多处，属于"同类事故还可能再犯"的结构性隐患。

### 方案
1. 中间产物统一落 `job_dir/_tmp/`，清理**只删该目录**，从机制上杜绝跨场景通配
2. 清理前 dry-run：打印待删清单 + 数量校验（异常数量直接中止）
3. `final_video_path` 入库前**断言文件真实存在**，且只允许指向 `*_final.mp4`

### 收益 / 成本
- 收益：杜绝最贵的一类事故（一次 3 小时）
- 成本：**低**

## 五、P4：可观测性 / 生产报告

### 问题
进度靠轮询 `/api/status`；失败原因散落在日志里；出片后无法回答"这批片子质量如何"。

### 方案
每个场景落库：`duration_ms` / `video_mode_used` / `retry_count` / `degrade_reason` / `vram_peak`。
出片时生成 `report.json`：

```json
{
  "scenes_total": 12,
  "true_video": 11,
  "degraded": 1,
  "degraded_scenes": [5],
  "total_seconds": 10234,
  "tts_engine": "stepfun"
}
```

### 收益 / 成本
- 收益：一眼判断这批片子能不能交付
- 成本：**低**

## 六、P5：工程化（长期健康）

| 项 | 现状 | 方案 |
|---|---|---|
| 单元测试 | pytest 未装，无任何测试 | 先补**纯函数**单测（`_stable_seed` / `_safe_decode` / 音色映射 / 文本分段），成本极低、收益最高 |
| CI | 无 | GitHub Actions：push 时跑语法扫描 + 单测 + **密钥扫描**（防 `.env` 误提交） |
| 启动自检 | 无 | 启动时校验模型文件存在且版本正确（T5 须为 Kijai 版、clip_vision 命名匹配正则），避免跑到一半才炸 |
| 配置校验 | 部分 | 启动时验证必需 env 并给出明确缺项提示 |

## 九、优先级建议

按「收益 ÷ 成本」排序，建议这个顺序推进：

| 顺序 | 项目 | 成本 | 收益 |
|---|---|---|---|
| 1 | **P2** TTS 并发+缓存 | 低 | 快 3-4 倍、省额度 |
| 2 | **P0** 静默降级治理 | 低 | 消除质量盲区 |
| 3 | **P3** 清理治理 | 低 | 杜绝 3 小时级事故 |
| 4 | **P4** 生产报告 | 低 | 可交付性判断 |
| 5 | **P1-a/b** 步数分级 + 超分可选 | 中 | 提速 30%+ |
| 6 | **P5** 单测 + CI | 中 | 长期健康 |
| 7 | **P1-c/d** 分辨率分级 + 并发 | 高 | 提速上限 |
| 8 | **P6/P7** 安全 + 产品向 | 中 | 体验与合规 |

**如果只做三件**：P0 + P2 + P3 —— 都是低成本，且分别解决「质量不可知」「慢且费钱」「最贵事故」三个最痛的点。
